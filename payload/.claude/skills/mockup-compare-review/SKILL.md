# モック比較レビュー

ピクセル差分で失敗した VC について、モック画像・実画面画像・差分画像を見比べ、差分の原因を
分類して人間が修正方針を決められるようにする。**この分類は助言であり、合否の判定ではない。**
CI の合否は `compareWithMockup` のピクセル差分だけで決まる。

## 入力

1. `mockup-compare-results/<change-id>/` が存在するか確認する
   - 無い場合はレビューしない。先にモック比較テストを実行するよう案内して終了する
     (例: `npx playwright test --grep "@<change-id>"`)
2. `node scripts/mockup-report.mjs <change-id>` を実行し、VC ごとの判定を確認する
3. 各 `<VC-ID>/meta.json` を読み、`pass: false` の VC **だけ**をレビュー対象にする。
   合格した VC はレビューしない
4. 対象の VC ごとに次を読む
   - `mockup.png`(モック)、`actual.png`(実画面)、`diff.png`(差分。赤系が差分ピクセル)
   - `meta.json`(差分率、許容差分率、サイズ不一致、フォント待ちのタイムアウト、実行開始時刻)
   - `openspec/changes/<change-id>/mockup-compare.md` の該当 VC の行(比較状態、比較範囲、マスク・非表示と理由)
   - 必要に応じてモック本体(`mockup/` 配下の HTML/CSS/JS)と、change の specs

## 分類

差分ごとに、次のいずれか 1 つを付ける。

| 分類 | 定義 | 典型例 |
|------|------|--------|
| `implementation-bug` | 実装の不具合。仕様とモックが一致しているのに実画面が違う | 色・余白・フォントサイズ・並び順・要素の欠落 |
| `mock-data` | モックのダミーデータとの差。表示しているデータの違いだけ | 一覧の行数や名前、件数、日付 |
| `intended` | 仕様で意図された差分。specs や design に根拠がある | モック作成後に specs で変更された文言やレイアウト |
| `mock-outdated` | モック側が古い・誤り。仕様が正しくモックが追従していない | 仕様で廃止された項目がモックに残っている |
| `environment` | フォントや描画環境による差 | Web フォント未読込(`fontsTimedOut: true`)、アンチエイリアス |

各差分には次を書く。

- **該当箇所**: 画像上の位置の説明(例: 「ヘッダー右上のユーザー名の左、約 40px 四方」)
- **根拠**: 分類の理由。specs / mockup-compare.md / モックの該当箇所を引用する
- **推奨アクション**: 誰が何をするか(実装の修正、モックの更新依頼、mockup-compare.md の変更提案など)

`intended` と `mock-outdated` は、specs のどのシナリオが根拠かを必ず書く。根拠が見つからない場合は
`implementation-bug` として扱い、人間に確認を求める。

## 出力: mockup-review.md

`openspec/changes/<change-id>/mockup-review.md` に、次の構成で書き出す。

```markdown
# Mockup Review: <change-id>

## 周回の推移

| 周回 | 比較の実行開始 | レビュー日時 | VC-001 | VC-002 |
|------|---------------|-------------|--------|--------|
| 1 | 2026-10-01T10:00:00.000Z | 2026-10-01 10:30 | 3.20% ✗ | 0.40% ✓ |
| 2 | 2026-10-02T09:00:00.000Z | 2026-10-02 09:20 | 0.80% ✓ | 0.40% ✓ |

## 周回 2(比較の実行開始: <全 VC の meta.json の startedAt の最古値>)

### VC-001: <mockup-compare.md の対応シナリオ>
- 差分率: 3.20%(許容 1.00%) / サイズ不一致: なし / フォント待ちタイムアウト: なし
- モック: `<meta.json の mockup>` / 実画面: `<meta.json の appUrl>`

| # | 分類 | 該当箇所 | 根拠 | 推奨アクション |
|---|------|---------|------|---------------|
| 1 | implementation-bug | ... | ... | ... |

**総合所見**: <この VC の差分をどう解消すべきかを 1〜3 文で>

## 周回 1(比較の実行開始: ...)
<前回までの結果をそのまま残す>
```

- 周回は新しいものを上に追記し、前回までの結果は**削除・書き換えしない**
- 「周回の推移」の表には、周回ごとの各 VC の差分率と判定(✓/✗)を記録する。合格してレビュー対象外の VC も差分率を記録する

### 同じ結果の二重転記を防ぐ

周回の「比較の実行開始」には、全 VC の meta.json の `startedAt` のうち最も古い値
(`mockup-report.mjs` が「実行開始(最古)」として表示する値)を使う。

レビューを始める前に、既存の mockup-review.md の最新周回の「比較の実行開始」と、今回の
その値を比べる。同じであれば、比較が再実行されていない。次の警告を出し、
新しい周回は追記しない。

> ⚠ 比較が再実行されていない: mockup-compare-results/<change-id>/ の実行開始時刻が前回レビュー時と同じです。モック比較テストを再実行してからレビューしてください。

## 禁止事項

- **閾値(maxDiffRatio)とテストコードを変更しない。** AI の分類で合否を変えてはならない
- `mock-data` や `environment` を理由にマスク・非表示・閾値を変えたい場合は、テストではなく
  **mockup-compare.md の該当 VC の変更**として mockup-review.md に提案し、人間のレビューに回す。
  提案には VC-ID、追加するマスク・非表示の対象(意図で書く)、理由を書く
- モック本体(`mockup/` 配下)を書き換えない。`mock-outdated` はモックの更新依頼として記録する
- 差分画像を見ずに meta.json の数値だけで分類しない
